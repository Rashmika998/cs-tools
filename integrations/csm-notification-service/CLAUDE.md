# CSM Notification Service

Go background worker (`net/http`, Go 1.26+) — a pure Kafka consumer, no inbound API beyond a health check. csm-portal-backend and customer-portal-backend publish domain events (case created, comment added, status changed, case assigned, incident created) directly to Azure Event Hub; this service's own consumers read them back and send the actual notification — email, a Google Chat alert, or a voice call. Extracted from `apps/csm-portal/backend/internal/notifications` — that backend no longer owns or calls any notification client.

This service used to also expose `POST /events` (an HTTP ingest endpoint the backends called, which this service then published to Event Hub itself) and, before that, an even earlier `POST /notifications` direct channel-command stub. Both were removed once it was decided the backends should own producing to Event Hub directly — one fewer network hop, and this service no longer needs any inbound HTTP surface for events at all. Don't re-add a producer-side HTTP endpoint here without confirming that decision has changed.

## Current scope — deliberately incomplete

The consume→dispatch path (event bus → `dispatch.Dispatcher`) **is real** — it sends actual emails, Google Chat alerts, and voice calls — but has one known, explicitly-flagged gap:

- **SMS and direct call channels are unused.** `TwilioClient.SendSMS` has no caller anywhere in this service; `MakeCall` is only invoked by `handleIncidentCreated`. Both clients/methods exist and are tested, just not wired to any event type yet.

A dead-letter topic **does** exist now (see "Event-driven notifications" below) — a record that exhausts the main consumer's retries is published there rather than dropped, and a separate DLQ consumer gets its own retry pass at it. There's still no third tier past that: a record that also exhausts the DLQ consumer's retries is logged and dropped for good.

Email *recipient* (audience) resolution is **not** a fixed env-configured list — every `case.*` payload carries its own `recipients` array, supplied by the caller (e.g. `csm-portal-backend`), since `dispatch.Dispatcher` has no way to resolve watchers/assignee/reporter itself. That's still short of "real" resolution (the caller has to already know the audience), but there's no `TEMP_*` env var or hardcoded test list to avoid pointing at real mailboxes anymore — `events.Validate` rejects any `case.*` event with an empty `recipients` list. This does **not** apply to `incident.created`'s Google Chat/call reactions, or `case.created`'s own Google Chat alert — there's no "recipient" concept to resolve for either the way there is for email; a Chat post goes to one shared space, not per-recipient. A publisher that knows the right Chat space/on-call number can still supply `product` (both types) or `callTo` (`incident.created` only) directly in the payload; one that can't (e.g. entity-service, which has no on-call/paging system or product→space mapping of its own) may omit either or both, and `dispatch.Dispatcher` substitutes its own configured `DEFAULT_CHAT_PRODUCT`/`INCIDENT_DEFAULT_CALL_TO` — see `internal/dispatch` below.

*Link* resolution is a separate, smaller thing this service now does do: `internal/recipientlinks.Resolver` (backed by `internal/entity`, a minimal customer-entity-service client) looks up each recipient's role and picks the portal-appropriate case link for them — see "Event-driven notifications" below. Don't conflate the two: this service still doesn't decide *who* gets notified, only *which link* a given recipient gets.

## Why no `Auth` middleware

The only route this service exposes is `GET /health` (Choreo's liveness probe), with no end-user or caller identity to check at all — everything else is Kafka consumption, not an HTTP request. Don't add inbound JWT/Bearer validation, or a new HTTP endpoint that would need it, without confirming this service is meant to have an inbound API surface again.

## Middleware chain

`SecurityHeaders → CorrelationID → Logger → Mux`

- `SecurityHeaders` (`internal/middleware/security_headers.go`): sets `X-Content-Type-Options: nosniff`, `Content-Security-Policy: upgrade-insecure-requests`, and `Strict-Transport-Security: max-age=31536000; includeSubDomains` on every response
- `CorrelationID` (`internal/middleware/correlation.go`): reads `X-CSM-Correlation-ID` from the incoming request or generates a UUID v4; ensures the ID carries a `cns-` prefix (CSM Notification Service) either way, without double-prefixing an ID that already has it; stores the ID in context for the slog handler; echoes the ID in the response header
- `Logger` (`internal/middleware/logger.go`): logs every completed request (method, path, status, elapsed) via slog

`middleware.ConfigureLogger()` must be called at startup — it wraps the default slog handler so every `slog.*Context(r.Context(), …)` call automatically includes `correlationID=<id>` when the context carries one. It also reads `LOG_LEVEL` (optional, defaults to `info`): set to `debug` to raise the handler's level so `internal/eventbus`'s `logDebug`-bridged kafka-go protocol chatter (join/sync/heartbeat/commit) actually reaches the log, instead of being silently dropped at the default `info` level — meant for one troubleshooting deploy (e.g. tracking down an unexpected `Unknown Member ID`/`Group Load In Progress` consumer-group error), not to stay on permanently.

## Notification channels

`internal/notifications` — one config/client pair per channel in its own file, since channels differ in upstream auth scheme:

- `EmailConfig`/`EmailClient`/`SendEmail` (`email.go`) — OAuth2 client-credentials auth against an external email notification service (`POST /send-email`)
- `GoogleChatConfig`/`GoogleChatClient`/`SendIncidentAlert` (`googlechat.go`) — a plain incoming-webhook URL per Google Chat space, no OAuth2 involved. `GoogleChatConfig.Spaces` is `[]GoogleChatSpace` (`{Product, WebhookURL}`), one space per product; `SendIncidentAlert` routes to the space matching `product` (case/whitespace-insensitive; unmatched returns an error, no fallback space)
- `TwilioConfig`/`TwilioClient`/`SendSMS`+`MakeCall` (`twilio.go`) — HTTP Basic Auth (Twilio Account SID/Auth Token; Twilio has no OAuth2 flow). One client, two methods, since sms and call are the same Twilio account/auth, just different REST resources (`Messages.json` vs `Calls.json`) via a shared private `do()`:
  - `SendSMS(ctx, to, body)` sends via the client's configured `MessagingServiceSid` if set (our account's real setup — a sender pool with opt-out/compliance handling), else its fixed `FromNumber`. If both are set, `MessagingServiceSid` wins
  - `MakeCall(ctx, to, message)` places a voice call that reads `message` aloud via a `<Say>` TwiML document built locally (`sayTwiML`, no external TwiML hosting needed) — always requires `FromNumber` as caller ID, since Voice has no `MessagingServiceSid` equivalent, regardless of whether `MessagingServiceSid` is set for sms. `<Say voice="..." language="...">` come from `TwilioConfig.Voice`/`Language` (`TWILIO_VOICE`/`TWILIO_LANGUAGE`, both optional — empty omits the attribute and uses Twilio's account default)
  - `TwilioConfig.APIBaseURL` overrides Twilio's REST API base (`TWILIO_API_BASE_URL`, defaults to `defaultTwilioAPIBaseURL` when empty — resolved once in `NewTwilioClient`, not read per-request). Not just a test seam: tests set it to an `httptest.Server` URL the same way a real deployment could point it at a regional Twilio edge endpoint

All three clients are constructed in `cmd/server/main.go` with `os.Getenv` (never `mustEnv`) for their config, since none is required for every deployment — a missing/invalid config only surfaces as an error the first time that channel is actually used. All three are handed to `dispatch.NewDispatcher`, which is the only thing that calls them (see "Current scope" above for `SendSMS`/`MakeCall`'s current usage gap).

A new channel gets its own `<Name>Config`/`<Name>Client` file in `internal/notifications` following the same pattern (or a new method on an existing client, if it shares that client's auth — as `MakeCall` does with `SendSMS`), then gets wired into `Dispatcher` for whichever event type(s) should trigger it — see "Adding a new event type" below.

`internal/entity` (the customer-entity-service client backing `internal/recipientlinks`) is **not** a notification channel and deliberately doesn't follow the pattern above — it's an upstream data client used to decide *which link* to put in an email, not something that sends a notification itself. Don't move it into `internal/notifications` or give it a `Send*` method.

## Event-driven notifications

This service is a pure consumer: csm-portal-backend and customer-portal-backend publish directly to Event Hub themselves (see `internal/events`'s package doc) — there is no HTTP ingest endpoint and no `internal/outbox` package here anymore. There *is* now an `internal/entity` package — don't confuse it with the removed `internal/entityservice` (that was an event-ingest thing, gone for good); `internal/entity` is new, unrelated, and exists only to back `internal/recipientlinks`'s link resolution (see below). Two packages implement the bus→consumer pipeline; `internal/notifications` (templates + channel clients) is the last-mile sender it calls.

- **`internal/events`** (`events.go`/`validate.go`) — the schema and its only remaining validation boundary. `Type` is one of `case.created`/`case.comment_added`/`case.status_changed`/`case.assigned`/`incident.created` (`KnownTypes`). `Envelope{Type, EntityID, Payload}` is the Kafka record value — `EntityID` is a case ID for the `case.*` types or an incident ID for `incident.created` (whatever the event is about, generically — it was named `CaseID` originally, renamed once `incident.created` made that name misleading), and is the Kafka partition key (see `internal/eventbus` below). `Payload` is `json.RawMessage`, decoded into the `Type`-matching payload struct (`CaseCreatedPayload`, etc.) by `Validate` and, again, by `dispatch.Dispatcher.Handle` for rendering. `Validate(entityID, t, raw)` — moved here from a since-removed HTTP handler — decodes strictly (`DisallowUnknownFields`) and checks required fields, plus (for the four `case.*` types) that the payload's own `CaseID` matches `entityID`; a mismatch would mean the payload was published keyed under the wrong case's partition. `Dispatcher.Handle` calls `Validate` before rendering/sending anything, since there's no handler upstream doing it before publish anymore — a caller that publishes a structurally invalid event now gets it retried, dead-lettered, and eventually dropped, rather than rejected synchronously at publish time. Payloads still carry denormalized display values (names, titles, a phone number) this service has no other way to obtain — that part hasn't changed. But case/comment **links** are no longer one of those denormalized values: the four `case.*` payloads carry `ProjectID`/`CaseID` (and `CommentID`, on `CommentAddedPayload` only — the other three have no comment to link to at publish time) instead of pre-built `CaseLink`/`CommentLink` strings, and `dispatch` resolves each recipient's own portal-appropriate link itself (see `internal/recipientlinks` below) rather than trusting a caller-supplied link. `Recipients []string` (audience) is unchanged — still caller-supplied, still not resolved here; see "Current scope" above for why that's a distinct thing from link resolution.
- **`internal/entity`** (`customer.go`) — a minimal, single-file, read-only entity-service client implementing only `POST /users/search` — unlike `apps/csm-portal/backend`'s own entity client (~60 passthrough methods for that backend's handlers), this one exists purely to back `internal/recipientlinks`'s role lookup. Its `do()`/OAuth2 setup mirrors `internal/notifications/email.go`'s shape, and — like that email client — its *credentials* don't follow a per-channel-independent pattern: `cmd/server/main.go` fills both `CustomerEntityConfig.TokenURL`/`ClientID`/`ClientSecret` and `EmailConfig.TokenURL`/`ClientID`/`ClientSecret` from the shared `OAUTH2_TOKEN_URL`/`OAUTH2_CLIENT_ID`/`OAUTH2_CLIENT_SECRET` env vars, not client-specific ones (`EMAIL_TOKEN_URL`/`EMAIL_CLIENT_ID`/`EMAIL_CLIENT_SECRET` used to exist and were removed) — mirroring csm-portal-backend's shared-OAuth2-app convention for *its* entity client. The real email-service and entity-service deployments this points at both authenticate every caller through the same shared gateway app (scoped via each client's own `*_SCOPES` var), which is why this isn't optional stylistic reuse — a dedicated `EMAIL_TOKEN_URL`/etc. genuinely doesn't exist for this deployment. Only `CUSTOMER_ENTITY_BASE_URL`/`CUSTOMER_ENTITY_SCOPES` (respectively `EMAIL_BASE_URL`/`EMAIL_SCOPES`/`EMAIL_FROM_ADDRESS`) are specific to each client. Google Chat and Twilio remain genuinely unrelated external providers with their own independent credentials — don't extend the shared-app treatment to them without the same kind of real-world reason. Deliberately carries no `x-user-id-token`/correlation-ID header forwarding — csm-portal-backend's version has both, to propagate a real end-user's identity/tracing through an HTTP request, neither of which exists in a Kafka consumer.
- **`internal/recipientlinks`** (`resolver.go`) — `Resolver.ResolveLinks(ctx, emails, projectID, caseID) ([]RecipientLink, error)` resolves each recipient's own portal-appropriate case link via `internal/entity`'s role lookup: a role in `CUSTOMER_ROLES` → the customer portal link, a role in `CSM_ROLES` → the CSM portal link, else a fallback chain (entity-service `userType` → CSM default) — see `ResolveLinks`' doc comment for the full reasoning, unchanged from when this lived in csm-portal-backend. Returns the *bare* case link only; `dispatch.commentLinkFor` appends a comment-specific `#<commentId>` fragment on top for `case.comment_added` (matching the CSM portal frontend's own comment-permalink format — the customer portal has no such fragment handling today, so the same suffix is simply inert there). A per-*recipient* decision, not per-event — the same notification can go to both a customer watcher and a CSM watcher at once, each needing a different link, which is why `dispatch.groupByLink` exists (see below) rather than rendering one shared email. `CSMLink(caseID) string` and `IncidentLink(incidentID) string` are the exception: no recipient, no role lookup, just `<CSMBaseURL>/cases/{caseID}` or `<CSMBaseURL>/operations/incidents/{incidentID}` directly — for `dispatch.handleCaseCreated`'s and `handleIncidentCreated`'s Google Chat alerts, both of which post once to a shared internal space rather than per-recipient, so there's no audience to resolve a role for in the first place. Neither takes a caller-supplied link — this service builds both itself, the same way it resolves every other portal link.
- **`internal/eventbus`** (`config.go`/`producer.go`/`consumer.go`/`logger.go`) — a thin wrapper around `github.com/segmentio/kafka-go` for Azure Event Hub's Kafka-compatible endpoint. This service used `github.com/twmb/franz-go` first, then switched to `kafka-go` specifically for its MIT license (franz-go is BSD-3-Clause) — both are pure Go (no cgo), keeping this service on Choreo's buildpack deploy with no Dockerfile either way; the swap is otherwise a wash technically (see the two known trade-offs below). `dispatch` and any other caller never import `kafka-go` directly — this package exposes its own `Record{Topic, Partition, Offset, Key, Value, IsFinalAttempt, NoMoreRetries}` and `Handle func(context.Context, Record) error` instead — `NoMoreRetries` is true only on a Handle call where there is truly no further attempt coming for this record's content anywhere, main topic or DLQ — either on `IsFinalAttempt` when `onExhausted` is nil, or on an extra cleanup call `processRecord` makes if `onExhausted` itself fails (nothing will ever redeliver this content then either, so `dispatch` still needs the chance to release its tracking); `dispatch` depends on this being distinct from `IsFinalAttempt`, see its own notes below, so `github.com/segmentio/kafka-go` is fully contained here. Auth is SASL/PLAIN with the literal username `"$ConnectionString"` and the Event Hub namespace's Shared Access Policy connection string as the password — this is Event Hub's own convention, not a real username. `Producer.Publish` keys every record by `EntityID` (`kafka.Hash` balancer) so all events about one case/incident land on the same partition and are processed in order — this service's own use of `Producer` today is only for publishing to the dead-letter topic (see below), since the case-events producer side now lives in the backends. `Consumer.Run` uses `FetchMessage`/`CommitMessages` (not the auto-committing `ReadMessage`) and only commits a record's offset after `Handle` succeeds (or its retries are exhausted and `OnExhausted` has run) — never before — so a crash mid-processing redelivers on restart instead of silently skipping. `Compression` is left unset (no codec) on the `Writer` — Event Hub's Kafka-compat layer rejected both idempotent producing and compressed batches with `UNSUPPORTED_FOR_MESSAGE_FORMAT` under the previous client (confirmed against the real namespace); `kafka-go`'s `Writer` has no idempotent-write feature to disable in the first place, and leaving `Compression` unset avoids the same rejection. `StartOffset: kafka.FirstOffset` is set explicitly for the same reason `kgo.ConsumeResetOffset(...AtStart())` was needed before — a partition with no committed offset should be read from the beginning, not the tail — though this happens to already be `kafka-go`'s own default. `logger.go` bridges kafka-go's `Logger` (routine, non-error chatter — protocol join/sync/commit messages, "N messages written" on every produce) to `slog.Debug`, and `ErrorLogger` (where kafka-go actually reports problems) to `slog.Error` — matching kafka-go's own severity split. Confirmed against the real namespace: routing `Logger` to `slog.Warn` instead (as this package originally did, to compensate for the previous Kafka client only having one log level) produced thousands of WARN lines a day for entirely normal operation. Don't reach for per-message-string filtering here again — bridging at the right level per kafka-go's own Logger/ErrorLogger split makes that unnecessary.
  - **`PartitionCount(ctx, cfg)`** dials the broker and calls `conn.ReadPartitions(cfg.Topic)`, returning how many partitions the topic actually has. Used only once, at startup (see `startConsumers` in `main.go`), to sanity-check a configured consumer count against reality — not read again afterward.
  - **`Consumer.Run(ctx, handle, onExhausted)`** — `onExhausted` (type `OnExhausted`) is called once a record has failed every one of `handleAttempts` (3) calls to `handle`; `Run` commits the record's offset right after regardless of `onExhausted`'s own outcome, since nothing will retry this record on this topic again either way. Passing `nil` (the DLQ consumer's own `Run` call — see below) falls back to logging at ERROR and dropping the record. The retry loop itself (`handleAttempts` calls, `handleRetryDelay` between them) is factored into the package-level `processRecord` function specifically so it's unit-testable without a real Kafka broker — `consumer_test.go` exercises it directly, injecting a short retry delay.
  - **Known trade-offs from the franz-go → kafka-go swap** (confirmed live against the real Event Hub namespace, not theoretical): (1) `kafka-go`'s consumer-group rebalancing only offers `Range`/`RoundRobin` balancers, no cooperative/incremental strategy like franz-go's `CooperativeStickyBalancer` — matters once more than one consumer instance shares a group (now the normal case, via `MAIN_CONSUMER_COUNT`/`DLQ_CONSUMER_COUNT` — see below), where a rebalance briefly pauses every partition instead of just the ones moving. (2) A graceful `Consumer.Close()` can take up to ~30s, matching `kafka.ReaderConfig.SessionTimeout`'s default — noticeably slower than before. If this service is ever deployed somewhere with a shorter termination grace period than server-shutdown-timeout + ~30s, that's worth revisiting (e.g. lowering `SessionTimeout` explicitly).
- **`internal/dispatch`** (`dispatch.go`) — `Dispatcher.Handle` implements `eventbus.Handle`: unmarshal the record as an `events.Envelope`, reject an unknown `Type` or a payload that fails `events.Validate` (see above), then switch on `Type` and unmarshal `Payload` into the matching struct. `NewDispatcher(email, googleChat, call, links, emailDebugMode, emailDebugRecipients, callSendingEnabled, defaultChatProduct, defaultOnCallNumber)` takes a fourth `linkResolver` param (satisfied by `*recipientlinks.Resolver`) alongside the three channel senders, plus a fifth bool/sixth `[]string` pair — `EMAIL_DEBUG_MODE`/`EMAIL_DEBUG_RECIPIENTS` in `cmd/server/main.go`. `EMAIL_DEBUG_MODE` (`os.Getenv(...) == "true"`, so unset means real sending — inverted from this service's usual `!= "false"` convention, deliberately, since "debug" reads as an opt-in) redirects the four `case.*` types' actual `SendEmail` calls to `emailDebugRecipients` instead of each event's real resolved recipients; unlike a killswitch, the email still actually sends, just to a safe test list, so a dev/staging deployment can be exercised end-to-end without risking a real mailbox. This replaced an earlier `EMAIL_SENDING_ENABLED` killswitch (`!= "false"` convention, same as `apps/csm-portal/backend`'s `AUTH_TOKEN_VALIDATOR_ENABLED`) that only logged instead of sending — that shape is gone for email; `sendPerGroup` (below) is where the redirect happens. A seventh bool, `callSendingEnabled` (`CALL_SENDING_ENABLED`, still the disable-entirely `!= "false"` convention), is the killswitch for `incident.created`'s Twilio call specifically — doesn't affect either type's Google Chat alert; calls have no debug-recipient equivalent, so they kept the simpler shape. The trailing `defaultChatProduct`/`defaultOnCallNumber` strings (`DEFAULT_CHAT_PRODUCT`/`INCIDENT_DEFAULT_CALL_TO`) are `handleCaseCreated`'s and `handleIncidentCreated`'s fallback values for their payload's own `Product`/`CallTo` when a publisher's payload omits them — added so entity-service, which has no on-call/paging system or product→Chat-space mapping of its own, can publish either event without knowing either value; a publisher that does supply its own value still takes precedence. `defaultChatProduct` applies to both event types (both trigger a Google Chat alert); `defaultOnCallNumber` only to `incident.created` (`case.created` has no call reaction). `events.Validate`'s `TypeIncidentCreated` case reflects the fallback: `Product`/`CallTo` are optional (empty is fine), but a non-empty `CallTo` must still match `e164Pattern` — this only relaxes "absent," not "malformed." `CaseCreatedPayload.Product` was already optional (`omitempty`) before this, unrelated to the fallback — it's a purely-display value in the case-created email template. Four types (`case.*`) now go through `groupByLink(ctx, recipients, projectID, caseID)` — calls `links.ResolveLinks`, buckets recipients into `map[string][]string` keyed by the link they resolved to (recipients sharing a link still batch into one email, at most two buckets today: customer vs CSM portal) — then `sendPerGroup(ctx, baseKey, groups, subject, render)` renders (via the matching `notifications.Render*` function, unchanged signatures — they already took `caseLink`/`commentLink` as separate params, so no template changes were needed) and sends once per distinct link, in sorted-key order for determinism, joining any per-group errors with `errors.Join`. `baseKey` (from `recordBaseKey(record)`, a SHA-256 hash of `record.Value` — the raw envelope bytes, not `topic/partition/offset` — shared by every idempotency-tracked channel in this file) plus each group's own `caseLink` key that group's own `claim`/`forget` entry: a real-world failure (a persistently-misconfigured email OAuth2 client) showed that without this, a retry caused by one still-failing group would resend every group that had already succeeded, and — for `case.created`, which also has a Chat alert — resend that too. `recordBaseKey` hashes content rather than Kafka coordinates specifically because a record dead-lettered to the DLQ topic is republished with the exact same `Value` but a brand-new `topic/partition/offset` (`cmd/server/main.go`'s `OnExhausted` calls `dlqProducer.Publish(ctx, record.Key, record.Value)`) — coordinate-based keys would make the DLQ's first attempt see an unclaimed key and resend an already-succeeded channel, which is exactly what a live incident surfaced (see `TestDispatcher_Handle_CaseCreated_RetryDoesNotResendSucceededChatAlert`). Every caller (`handleCaseCreated`/`handleCommentAdded`/`handleStatusChanged`/`handleCaseAssigned`) calls `forgetEmailGroups(baseKey, groups)` once it knows no further retry is coming anywhere (the whole call succeeded, or `record.NoMoreRetries` — deliberately not `record.IsFinalAttempt`, which is only true per-topic and would release tracking one tier too early, right before the DLQ redelivery that needs it) — never on a single group's own success alone, which would release tracking while some other group (or, for `case.created`, the Chat alert) is still failing and about to trigger another retry that would then re-arm and resend the already-succeeded group. When `emailDebugMode` is true, `sendPerGroup` still runs `groupByLink` against the event's real recipients (so a broken resolver/entity-service still surfaces as an error) but calls `SendEmail` with `emailDebugRecipients` in place of each group's real recipients — still a real send, just redirected; the per-group tracking key is still based on the real resolved `caseLink`, unaffected by the redirect. If `emailDebugMode` is true and `emailDebugRecipients` is empty (misconfigured), that group is marked done and skipped (logged) rather than calling `SendEmail` with zero recipients — retrying wouldn't fix a missing debug-recipient config. `commentLinkFor(caseLink, commentID)` appends the `#<commentId>` suffix (empty `commentID` → bare link, used by the three non-comment types).

`handleCaseCreated` additionally posts a Google Chat alert — the same `GoogleChatClient.SendIncidentAlert` call `incident.created` uses below; its own doc comment already covers "a newly created incident/case" for exactly this reuse — independent of the email step above (a failure in one is joined with, but doesn't suppress, the other, matching `handleIncidentCreated`'s two-independent-reactions shape). Its `portalURL` is `links.CSMLink(caseID)` (a `linkResolver` method, `recipientlinks.Resolver.CSMLink`) rather than a `groupByLink`-resolved link — a Chat post has no per-recipient audience to resolve against, so it always targets the CSM portal's case link, with no customer-portal equivalent. `product` falls back to `defaultChatProduct` the same way `handleIncidentCreated`'s does (see above), and — also the same as `handleIncidentCreated` — the Chat alert is skipped (logged) rather than attempted with an empty product when both the payload's own value and `defaultChatProduct` are unset. The Chat alert has its own idempotency-tracked `chatKey` (`baseKey+"/chat"`), the same mechanism `handleIncidentCreated`'s two channels use — `handleCaseCreated` releases `chatKey` and every email group's key together, in one place, once `len(errs) == 0` (the whole call is about to return nil — no more retries coming) or `record.NoMoreRetries`, never on any single channel's own success alone, and never on `record.IsFinalAttempt` alone either (see `handleCaseCreated`'s own doc comment for why that specific ordering matters — two separate real bugs, caught by regression tests before landing: releasing on a single channel's success, and releasing on the main topic's own final attempt when a DLQ tier is still coming). `handleIncidentCreated` builds its own `portalURL` the same way — `links.IncidentLink(entityID)` (`entityID` is `Handle`'s already-decoded `env.EntityID`, threaded through as a new parameter since `handleIncidentCreated` previously only received the payload) — rather than the `IncidentCreatedPayload.IncidentLink` field an earlier version of this schema had; a publisher (e.g. entity-service) only needs to publish the fact that an incident was created, not know this service's own portal URL configuration, matching the `case.created`/`CSMLink` precedent exactly.

`incident.created` skips the email/link-resolution path entirely — no template, no email, no `groupByLink` — it calls `GoogleChatClient.SendIncidentAlert` and `TwilioClient.MakeCall` from the payload's own `Product`/`CallTo` fields, substituting `defaultChatProduct`/`defaultOnCallNumber` when either is empty (see above), attempts both even if one fails, and combines their errors with `errors.Join`. When `callSendingEnabled` is false, the call step logs instead of invoking `MakeCall` and is still treated as succeeded (`markDone` still runs) — the disable-entirely shape `sendPerGroup`'s email sending used to have before `EMAIL_DEBUG_MODE` replaced it with a redirect (see above); calls have no debug-recipient equivalent, so this keeps the simpler shape — so a disabled call doesn't retry forever; the Google Chat alert is unaffected. A non-nil return from `Handle` is what triggers `eventbus.Consumer`'s retry (and, on exhaustion, `OnExhausted`) — which is exactly why `handleIncidentCreated` needs its own per-channel idempotency tracking (`Dispatcher.done`, keyed by `recordBaseKey(record)+"/"+channel` — a content hash, not `topic/partition/offset`): without it, a persistently-failing call would cause the already-succeeded chat alert to be resent on every retry too. This was a real bug caught by testing against Twilio being unconfigured — see that function's doc comment before changing this. `done` entries are released either when both channels have succeeded, or when `record.NoMoreRetries` is true — the latter matters because a channel that never succeeds would otherwise never hit the "both succeeded" branch, leaking its tracking entry forever; `NoMoreRetries` says no further retry is coming for this record's content anywhere (main topic or DLQ), so it's safe to stop tracking regardless of outcome. `record.IsFinalAttempt` is deliberately NOT used for this release: it's only true relative to the current topic, and a record dead-lettered off the main topic is republished with the exact same `Value` (so the exact same content-hashed key) under a fresh `topic/partition/offset` on the DLQ topic — releasing on the main topic's own final attempt would let the DLQ's first attempt reclaim and resend an already-succeeded channel, which is a real production incident this was fixed in response to (a case.created record whose email kept failing got dead-lettered, and its already-sent Chat alert got reposted once the DLQ consumer picked it up). `Dispatcher.done` is per-process, in-memory either way — a restart between the main topic and DLQ deliveries still loses tracking (the accepted at-least-once trade-off `Dispatcher.done`'s own doc comment describes), but a live process now correctly carries a channel's success across that hand-off instead of resetting at the topic boundary.
- **Dead-letter queue** — a record whose `Handle` call fails on all `handleAttempts` attempts is published to `EVENT_HUB_DLQ_TOPIC` (see `cmd/server/main.go`'s `toDeadLetter` func, `eventbus.OnExhausted`) instead of being dropped. This service also runs a second, independent consumer group against that DLQ topic, using the *same* `dispatcher.Handle` — so a dead-lettered record gets its own fresh `handleAttempts` retry pass — but with `onExhausted=nil`, so a record that fails there too is logged at ERROR and dropped for good; there is deliberately no third tier. If `EVENT_HUB_DLQ_TOPIC`'s Event Hub doesn't exist yet in Azure, provision it before deploying — this service does not create topics itself.
- **`cmd/server/main.go`** — constructs `eventBusCfg`/`dlqCfg` from `mustEnv` (not `os.Getenv`): unlike the notification channels, broken event bus config should fail startup loudly since consuming (and dead-lettering) events is this service's core job. `startConsumers(ctx, name, cfg, group, count, handle, onExhausted)` first calls `eventbus.PartitionCount` and logs a warning (never fails startup) if `count` exceeds the topic's real partition count — Kafka just leaves the excess consumers idle rather than erroring, so a warning is the right severity — then starts `count` independent `eventbus.Consumer` instances, each in its own goroutine, all joining the same consumer group; Kafka's own rebalancing splits the topic's partitions across however many are actually running. Called twice: once for the main topic (`MAIN_CONSUMER_COUNT`, `toDeadLetter` as `onExhausted`) and once for the DLQ topic (`DLQ_CONSUMER_COUNT`, `onExhausted=nil`). Both sets of consumers are closed explicitly on shutdown (after `ctx` is canceled, before the HTTP server's own `Shutdown`) so each instance leaves its consumer group gracefully rather than waiting out the session timeout.

### Adding a new event type

1. **Payload struct** (`internal/events/events.go`) — add a `<Name>Payload` struct with every field its eventual `Render*` call needs (plus `Recipients []string` if it emails anyone — see `CaseCreatedPayload`), and a new `Type` constant added to `KnownTypes`. If it emails anyone, don't add a pre-built link field — add `ProjectID`/`CaseID` (for `groupByLink`) and, only if there's a specific comment to deep-link to, a `CommentID` (see `CommentAddedPayload`); `dispatch` builds the link itself via `internal/recipientlinks`
2. **Validation** (`internal/events/validate.go`, `Validate`) — add a case decoding and checking the new payload's required fields
3. **Dispatch** (`internal/dispatch/dispatch.go`) — add a case in `Handle`'s switch and a `handle<Name>` method following the existing ones' shape
4. **Template**, if new — see "Adding a new channel"'s sibling process in `internal/notifications`
5. **Tests** — add validation tests (`internal/events/validate_test.go`) and dispatch tests (`internal/dispatch/dispatch_test.go`) following the existing per-type cases

## SLA timer engine

`internal/slaengine` is a separate consumer/producer pair from `internal/dispatch` — ported from a standalone POC, adapted to this repo's real architecture (durable state on entity-service, since this service has no database of its own). It shares `EVENT_HUB_TOPIC` with `dispatch.Dispatcher`'s main consumer (a different consumer group, so it gets its own full copy of every record) rather than getting a dedicated topic — no new Azure Event Hub topic needed for this feature.

- **`client.go`** — `EntityClient`, a narrow HTTP client for entity-service's `sla_clocks` endpoints (`POST /cases/{caseId}/sla-clocks`, `GET .../sla-clocks/{clockType}`, `PATCH .../tiers/{tier}` with `{"status":"reached"}`). Mirrors `internal/entity.CustomerEntityClient`'s `do()`/OAuth2 shape exactly, but is a genuinely separate client — entity-service's `sla_clocks` API is unrelated to `internal/entity`'s `POST /users/search`.
- **`redis.go`** — `WakeIndex`, a thin wrapper around one Redis ZSET (key `sla:wake`, member `"<caseId>|<clockType>|<tier>"`, score = the Unix timestamp that member becomes due). **First Redis dependency in this repo** — no existing pattern to conform to. Local `REDIS_ADDR` for now; Azure Cache for Redis later needs no code change, only the connection details, since both speak the same wire protocol.
- **`engine.go`** — `Engine.Handle` is this feature's consumer entry point (its own `eventbus.Consumer`, `SLA_CONSUMER_GROUP`/`SLA_CONSUMER_COUNT` in `cmd/server/main.go`): decodes the envelope, silently ignores anything that isn't `events.TypeSLAClockRegister` (this consumer shares a topic with unrelated types — must skip, not error, the mirror image of `dispatch.Handle`'s own no-op case for `sla.clock.register`/`sla.tier_reached`, see below), then registers a clock per entry in the payload's `Durations` map and seeds three Redis wake entries (50/75/100% of the duration) per clock. `Engine.Tick(ctx, now)` — factored out of `RunTicker` exactly like `eventbus.processRecord` is factored out of `Consumer.Run`, so it's testable by calling it directly with a controlled `now` rather than a real ticker — scans the wake index for due members, checks each clock isn't paused (`EntityClient.GetClock`), records the tier reached idempotently (`SetTierReachedIfUnset`), publishes `events.TypeSLATierReached` via a second `*eventbus.Producer` (reusing `eventBusCfg`'s topic), and only then removes the wake entry — in that order, so a publish failure leaves the entry in place and retries next tick rather than silently losing it (the entity-service write already happened and is itself idempotent, so retrying it is harmless). `RunTicker(ctx, interval)` is a plain `time.NewTicker` loop, started as its own goroutine in `main.go` — the first ticker-based background loop in this service (everything else is a blocking consumer poll loop).
- **No SLA duration policy exists anywhere in this system.** `events.SLAClockRegisterPayload.Durations` is caller-supplied (clock type → Go duration string, e.g. `"response": "2h"`) — the same stand-in the POC used for a not-yet-decided severity → duration policy. Nothing in `cmd/server/main.go` or entity-service computes a duration from case severity; whatever eventually publishes `sla.clock.register` with real values (possibly entity-service itself, once its own uninvoked `EventPublisherService` — see its own `CLAUDE.md` — gets wired into case creation) is a separate, later step.
- **`dispatch.go`'s `Handle` switch has an explicit no-op case for `events.TypeSLAClockRegister`/`events.TypeSLATierReached`** — both are in `KnownTypes` (so `IsKnown()` passes) and have `Validate` cases (so a genuinely malformed one still gets rejected), but `dispatch.Dispatcher` itself has no reaction to either; returning `nil` rather than falling through to the switch's `default` is required, since erroring would burn the main consumer's retries and dead-letter an event that was never broken, just not this consumer's concern. Keep this in mind before adding a new `slaengine`-only event type: it needs the same no-op treatment in `dispatch.go`, or every such event gets retried and DLQ'd for nothing.
- **Accepted trade-off: `processDueMember` gates publishing `sla.tier_reached` on `EntityClient.SetTierReachedIfUnset`'s `alreadyReached`** (entity-service's `UPDATE ... WHERE ... IS NULL` decides atomically which caller actually caused the transition) — skip publishing, just drop the wake entry, when some earlier call already claimed the tier. This is a deliberate choice, not the obviously-safe option: `alreadyReached` only reflects the database claim, not whether a notification was ever actually delivered, so a caller whose own publish to Event Hub failed (or crashed) after winning the claim will, on later rediscovery, see `alreadyReached=true` and skip publishing — permanently losing that tier's notification, not just delaying it. Accepted anyway because a publish failure to Event Hub is judged rare, and duplicate-free rediscovery matters routinely, not just for a rare multi-replica race: it's what makes a planned (not yet built) Redis-outage fallback — falling back to asking entity-service directly which tiers are overdue when Redis itself is unreachable — usable at all, since Redis recovering after an outage rediscovers every wake entry that survived the outage, and without this gating every one of them would duplicate-publish on every recovery. If this trade-off ever stops being acceptable (Event Hub reliability turns out worse in practice, or this service starts running multiple replicas), the real fix is a durable delivery/outbox state tracked separately from the reached-claim, with a lease/expiry so a failed attempt's slot can still be retried by someone else — not built, see `Tick`'s own doc comment for the full reasoning.

# from integrations/csm-notification-service

## Commands

```bash
go vet ./...              # vet
go test -race ./...       # vet + race-detector tests
go build -o server ./cmd/server   # compile
govulncheck ./...         # checks dependencies against Go's official vulnerability database
```

`govulncheck` does call-graph analysis, not just "is a vulnerable package present" — it only flags a vulnerability if your code's own call graph actually reaches the vulnerable function, so a clean result means more than a plain dependency-list scan would. If it errors with `package requires newer Go version go1.26 (application built with go1.25)`, the installed `govulncheck` binary itself was built with an older Go than this module's `go 1.26.0` directive — reinstall it with a toolchain that matches or exceeds that, e.g. from a directory using that toolchain, or `GOTOOLCHAIN=go1.26.5 go install golang.org/x/vuln/cmd/govulncheck@latest` (adjust the patch version to whatever's cached under `$(go env GOPATH)/pkg/mod/golang.org/toolchain@v0.0.1-go1.26.*`), then invoke it the same way if it still misdetects its own Go version.

## Adding a new channel

1. **Client** (`internal/notifications/<channel>.go`) — add `<Name>Config`/`<Name>Client`/`Send<Thing>` following `email.go`'s or `googlechat.go`'s shape, whichever auth scheme is closer
2. **`cmd/server/main.go`** — construct the new client from env vars (use `os.Getenv`, not `mustEnv`, unless the channel truly must be configured for the service to start), and pass it into `dispatch.NewDispatcher`
3. **`dispatch.Dispatcher`** — add a field for the new client, and call it from whichever `handle<Type>` method(s) should trigger it (a new field on an existing event's payload if it needs new caller-supplied data, or a new event type entirely — see "Adding a new event type")
4. **Payload fields**, if the new channel needs new ones on an existing event — add them to the relevant `*Payload` struct in `internal/events/events.go`; there's no `openapi.yaml` schema for these anymore (it only documents `/health` now — see "Event-driven notifications"), so that struct's own doc comments are the source of truth for the wire shape
5. **Tests** — add dispatch tests for the new channel's send path, following the existing per-type cases in `dispatch_test.go`

## Security

- **Never commit secrets** — client IDs/secrets, webhook URLs, service URLs with credentials, and the Event Hub connection string must not appear in source code or config files; use environment variables
- **No sensitive data in logs** — log only IDs and error summaries; this includes not logging the Event Hub connection string or full record values that might carry PII — every `case.*` payload's `recipients` array is real email addresses now (not a fixed test list), so this applies more directly than before. `internal/recipientlinks`'s role-lookup warnings are deliberately keyed on `caseID`/`roles`/`userType`, never the recipient's email — this was a real CodeRabbit-caught PII finding when the code lived in csm-portal-backend (fixed in `ea84cdf2e`); it must not be reintroduced now that the code has moved
- **No app-level inbound auth** — this is intentional (see above), not an oversight; don't "fix" it by bolting on JWT validation without confirming this service is meant to have an inbound API surface again
- **Input validation** — `events.Validate`, called from `dispatch.Dispatcher.Handle`, is now the only validation boundary this service has (no HTTP handler upstream anymore) — keep rejecting unexpected input there (JSON structure, required fields) rather than letting a malformed record reach a notification client
- **TwiML injection** — `MakeCall`'s spoken message is caller-supplied text, not trusted markup. `sayTwiML` (`twilio.go`) builds the `<Say>` document by `encoding/xml`-marshaling a typed struct (`twimlResponse`/`twimlSay`), never raw string concatenation — a message containing TwiML-shaped text (e.g. `</Say><Redirect>...`) must render as literal spoken text, not inject a different verb. `Voice`/`Language` go through the same struct as `xml:"...,attr"` fields, so they get correct attribute escaping too, even though today they're only ever operator-supplied config, not request input. Keep using `encoding/xml` struct marshaling (not string concatenation) for any future TwiML-building code in this package
- **Security fixes in PRs** — describe security-related changes in neutral functional terms only, not called out as security fixes in the title/description
- **Run `govulncheck ./...` on dependency changes** — alongside `gosec` (which only analyzes this repo's own code), run this whenever `go.mod`/`go.sum` changes (a new dependency, or a version bump) to catch known vulnerabilities in the dependency tree itself. It must report 0 vulnerabilities reachable from our code before opening a PR; a vulnerability present in a dependency but not reachable through anything we call is worth noting in the PR but isn't a blocker — see `internal/eventbus`'s `klauspost/compress` bump for a real precedent (GO-2026-5841, upgraded proactively even though unreachable, since the fix was free)
